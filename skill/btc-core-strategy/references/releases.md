# 版本、节点与恢复

源码及方法来自 `york6668/btc-core-strategy` 的同一个提交；`market-roles` 用 submodule 固定提交。生产数据始终留在节点配置的 `project_dir`、reader 数据路径及既有 Codex 本地目录。

每轮先用本机版本入口执行 `enter --run-id <真实运行ID>`。返回物理 `release`、`skill`、`methods`、`project_dir` 和 `node_config` 路径。设置 `BTC_RELEASE`、`BTC_PROJECT`、`BTC_NODE_CONFIG` 和节点 `python` 对应的 `BTC_PYTHON`；随后每次命令均带这些值。不能从会变化的 Skill 链接或 `current` 再次选择代码。方法中的脚本路径都相对于本轮 `BTC_RELEASE/skill/btc-core-strategy`。

独立自动化节点在 `enter` 中以当前原生 `CODEX_THREAD_ID` 验证登记根及共享用量范围，成功后把最小 `native_contexts` 写入原 runs 版本登记；同一身份重复进入不重复追加，真正恢复到另一原生上下文才追加其已验证身份。该字段不代替原生自动化触发或 token 记录，不创建第二份调度台账，也不改变原 `run_id`。空身份或本机原生元数据缺失是明确计量缺口，不能用业务 run-id 猜 thread ID。已 FINISHED 的相同运行仍只读返回，升级与计量接入不重开旧轮、不改变 UNKNOWN 或旧运行的固定版本。

安装、激活及进入运行共同核对原 `export-manifest.json` 的必需源码、Skill 和方法文件；缺失或越界时停止，不写入新的 ACTIVE 运行。ACTIVE 只证明本轮代码已固定且声明文件完整，模型仍须读取对应正文，服务、数据、研究及报告效果分别核验。源码 `strategy_v4.py --help` 与子命令帮助在本机解析，不读取节点配置、同步事实或进入 Docker writer；宿主解释器适配器仍须读取原节点配置以选择解释器。`report-context`、`report-care` 等正常业务命令仍走既有节点桥接及其持久操作，不能当作无副作用帮助探测。

当前新运行使用其固定的兼容发布承担现有职责，按原来源读取历史请求与成果；旧方法版本、路径及线程本身不阻止新阶段。已在途执行、原投递效果和 UNKNOWN 的身份与版本绑定继续保留；不能中途换码或重放未知效果。下面的 resume-context 用于明确恢复既有固定执行上下文，不是全部历史材料进入当前职责的前置。

研究请求或投递任务创建后，用 `bind-context --run-id <原运行ID> --context <真实request_id或job_id>` 保存版本引用。恢复时 `enter --run-id <本次恢复ID> --resume-context <原上下文ID>` 返回原版本。原证据、研究阶段、代理、UNKNOWN 尝试和回读身份仍由原策略记录拥有；版本引用不代表完成、批准或送达。已有上下文没有版本记录时，先根据该上下文实际使用的代码版本补回引用，不猜测最新版，也不重开研究或重发。

本轮结束用 `finish --run-id <原运行ID>`。崩溃留下的 ACTIVE 标记由恢复任务先接续，确认本轮已停止后再 finish；不能按过期时间假定工作已结束。旧版本不自动清理，未完成研究和投递可以继续使用。

当旧研究因已确认的程序兼容缺陷无法登记，先在修复版本验证原冻结材料，再使用 `repair-context --context <原request_id> --from-commit <当前恢复版本> --to-commit <已安装修复版本> --reason <具体缺陷与复验依据>` 追加修复映射。原始绑定及修复历史保留；仅之后新建的恢复运行读取指定修复版本，已有运行仍固定原版本。该入口只接受原字节身份有效的研究请求，拒绝正在恢复的上下文、版本冲突和不可读的内容 revision；不能用于投递或通过安装自动触发。原 request/issue/代理/冻结成果和 parent_independent 不变，登记后继续原真实审阅与采纳，不生成批准或替换历史。普通恢复仍沿原版本，UNKNOWN 投递无此例外。

维护时修改源码仓库并运行相称验证，提交、推送后按已验收的版本组合决定是否更新 `market-roles` 的 submodule，已固定依赖不随独立发布自动升级；用指定提交安装本机独立发布目录。安装从 Git 提交的原导出清单取得正式源码与方法，核源码完整性及节点解释器语法后才切换；行为回归按本次明确候选在临时位置完成，不将案例或测试 reader 设为长期安装依赖。运行中只暂存待切换版本，在轮次间隙 `activate <commit>`；回退使用同一命令指向原版本。切换不改任何策略数据、账户事实、游标、报告与运行历史，失败保留当前版本。没有节点访问能力时保留待部署状态。

重复激活当前同版仅返回现状，保留上一次实际切换的 previous、时间及另一个待激活版本，不因已有运行重新登记切换。当前包损坏时，可在原运行间隙切换到已验证完整的版本；旧损坏目录与其上下文保留，不修写历史或让旧上下文静默改用新代码。

外层 v4 schema 不变。新代码可读内容 revision 1–9，新入口采用 revision 9；旧上下文保留原内容与固定代码。正式迁移只随真实评估和采纳，不自动写入配置决定；不改资产、历史、研究或 UNKNOWN 状态。RELEASE.json 声明 content_contract，可读范围不含当前正式 revision 的代码不能激活；旧上下文仍可 enter --resume-context 接续。恢复与备份沿现有节点机制，不通过回滚旧数据实现代码回退。

安装验证仅证明代码和接口。自然验收沿原定时任务观察：固定代码提交、方法路径与数据路径正确；既有研究接续；正式状态、发送与实际助手回读分别成立。缺少真实报告必要性时不为了验收制造报告或重新研究。

运行版 reader 只承担其实际运行职责。安装器不要求 reader 的测试源码；组合行为变化由本次验证使用明确版本的真实 reader，临时材料按项目生命周期处理，不改变节点运行路径。

冻结数值兼容解释器由节点持久管理，`frozen_market_python` 与可选 `frozen_market_python_version` 指定已经验证的运行时。应用缓存目录与临时解包路径不承担长期恢复依赖；移交时保存完整运行时依赖并验证精确复算。宿主兼容版本不等于容器主版本，按实际执行节点配置，不改写原材料或放宽数值校验。

`btc-python` 的宿主适配器只识别本轮发布目录中的 `strategy_v4.py`，由该策略入口按原桥接规则处理正常业务调用；自写预检脚本、`-` 和 `-c` 仍使用节点的 `native_python`，不会自动进入 core，也不自动采用 `frozen_market_python`。公开结果及报告预检沿正常策略 CLI 或已核验的正式 core；宿主需复算冻结行情时使用现有 `market_runtime.validate_file` 的环境绑定。回执记录实际解释器、源码与原件摘要；不同候选或当前文件通过不能覆盖先前失败，也不能单凭版本差异断言唯一根因。无需因此更换系统 Python、切换节点或修改冻结数值。

候选工作区、离线验证包和正式节点采用分别说明。要求报告验收后采用时，先保留工作区候选；不得仅因测试完成更新 current/pending 或提交到会被运行器自动采用的发布入口。报告候选不登记为自然送达，不改变原验收窗口。
